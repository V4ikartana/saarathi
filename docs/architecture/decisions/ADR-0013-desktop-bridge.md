# ADR-0013: Desktop integration through a stdio JSON-RPC bridge and detached drivers

- Status: Accepted
- Date: 2026-10-19

## Context

Saarathi Desktop (Tauri + React) must control the existing engine without duplicating its logic or state, keep runs
going when the window closes or the user switches sessions, avoid a network listener, and never parse human-readable
CLI output as its contract.

## Decision

- A new `saarathi bridge --stdio` command speaks newline-delimited **JSON-RPC 2.0, protocol 1** over stdin/stdout.
  It calls the engine as a library. The Tauri shell starts it as a child process and relays messages, and nothing
  listens on a port.
- The bridge never drives runs in its own process. It starts **detached drivers** (`saarathi resume --run R
  --non-interactive`), which the existing engine lock limits to one per project. Execution therefore survives window
  close and bridge crashes, and the next bridge reattaches from state.
- Live updates come from tailing the existing `events` table by `seq`. Clients resubscribe from their last seen `seq`
  after a disconnect.
- Conversation sessions are two new tables in the existing `state.db` (migration 5). A session groups runs. The
  conversation it shows is rendered from real run state and events, never generated by the UI.
- Mutating requests carry idempotency keys. The engine stays the only authority for transitions, routing and approvals.

## Consequences

- No new database, server or streaming system. The CLI and desktop see the same state.
- Updates arrive with polling latency (about 200 ms).
- Stop and cancel are distinct operations with defined semantics (see docs/desktop/architecture.md §4).
- The desktop app depends on an installed `saarathi` until a bundled sidecar exists (M5).
